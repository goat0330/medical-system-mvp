# 结算清单与仓库调研落地结论

更新时间：2026-09-22

## 1. 结算不是一个金额函数

国家医保局 2021 年修订通知明确了《医疗保障基金结算清单》和填写规范。结算清单应由住院诊疗、诊断/手术编码、费用明细和支付信息共同组成，而不是由 DRG/DIP 分组结果直接推导全部字段：

- https://www.nhsa.gov.cn/art/2021/8/30/art_37_5871.html
- https://www.nhsa.gov.cn/module/download/downfile.jsp?classid=0&filename=f46c5c96e954469c9eda6755cab9f4e9.pdf

因此本 MVP 采用四步：

    清单生成
      → 清单质控
      → 申报快照/批次
      → 医保反馈/对账

## 2. PDF 映射策略

医保结算清单（193项）.pdf 作为字段语义和展示分组依据，分成：

- 基本身份与结算标识
- 住院过程与出入院
- 诊断
- 手术/操作
- 临床过程
- 出院
- 费用汇总
- 医保支付与经办机构

当前代码用稳定的 snake_case 字段 ID，不伪造官方字段号。病案号、医保编号、清单流水号、业务流水号、票据代码/号码等标识严格分开；费用分类与支付拆分也严格分开。PDF 文件名中的“193 项”不能替代完整官方字段代码字典，后续拿到接口字典后再补 code mapping。

当前代码已落地 7 组、103 个可运行语义字段；其余字段保留在待核验边界内，不能把 103 个字段冒充为完整 193 项官方接口映射。

## 3. 开源仓库借鉴

最有价值的是 I-ONE medical insurance：https://github.com/jerry317395616/ione_medical_insurance 的对象链和服务边界：

- IONE Settlement List：版本、来源、总额、医保金额、个人负担和 payload/result JSON。
- IONE Claim Snapshot：提交前冻结病例与清单输入，保存数据版本。
- IONE Claim Batch：申报批次、申报金额、支付金额、扣款和反馈码。
- IONE Insurance Response：保存医保反馈。
- IONE Settlement Reconciliation：计算 paid + deduction - claim 的差异并决定是否平衡。
- IONE Interface Definition / Integration Run：接口方式、幂等键、请求结果和失败重放。

本项目复用这个思路，但用零依赖 ES module 实现本地 mock，便于直接演示，不引入 Frappe、MongoDB 或真实医保网关。

## 4. 真实联调替换点

公开的国家医保信息平台接口材料把结算清单上传定义为 3600 交易：一位患者一次上传，setlinfo 为单行，其它明细可为多行；重复上传以最新数据覆盖。MVP 的 mock 快照已保留这三个接口语义，但没有伪造真实鉴权和网关地址。参考接口说明：https://ylbzj.cq.gov.cn/bmfw_535/xzzq/202302/P020230206548428046833.pdf

真实平台联调时，只替换 mock adapter 的四项，不改前端病例和清单模型：

1. 报文/字段 code mapping；
2. 机构、险种、统筹区和接口鉴权；
3. 申报批次发送与异步反馈；
4. 反馈码、扣款明细和对账入账。

在这些材料未到位前，界面必须显示 mock / 可回放，不能写成“已结算”。
